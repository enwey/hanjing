## 实现

- `schema-sync.js`、`scripts/schema-reference.mjs`：在同一 MySQL 服务的隔离空库运行当前代码的建表与迁移，以最终结构比对业务库。支持创建缺表、补齐/删除/修改字段、顺序、索引及约束；保留未纳管整表。
- 预览指纹校验代码及现有结构；数据库命名锁阻止并发同步；备份受影响表与原结构元数据后执行 DDL，严格模式阻止静默截断，最终核验一致才返回成功。
- 自动生成索引按语义及数量比较，避免 MySQL 重建外键改名导致误报；字段字符集/排序规则继承表示也进行等价规范化，不改写引号内默认值。
- `db.js`：显式同步入口接入新流程；参考库收集非幂等预期 DDL 错误；手机号修改不再重复创建 UNIQUE 索引，CRM 旧字段重命名先查存在性。
- `routes/admin.js`：沿用 `database:sync` 权限，区分预览和执行，审计差异与备份库，保留错误状态。
- 管理后台数据库工具：先预览待删字段及定义差异，确认维护停写后提交；展示备份库，去除“绝对不会删除数据”的旧提示。
- 使用及恢复边界见 `hanjing-clinic-backend/schema-sync.md`。

### SCHEMA-REG-01：普通字段因注释文本被漏备份

- 状态：回归通过。
- 原风险等级：高（P1），影响删除前备份的完整性。本轮隔离回归已验证修复；生产部署不在本轮验收范围。
- 位置：`hanjing-clinic-backend/schema-sync.js` 的 `backupTables()`（修复前第 190 行）。
- 前置条件：当前代码不再定义的普通可空字段，其注释中含有 `GENERATED ALWAYS` 字样；该字段有实际业务值，并非 MySQL 生成列。
- 验证方法：在隔离库挂载真实后台路由，使用具有权限的测试账号执行预览和同步，再查询返回的备份库。
- 复现步骤：
  1. 隔离库初始化后给 `users` 添加 `legacy_import_note VARCHAR(80) NULL COMMENT 'GENERATED ALWAYS by the legacy importer'`。
  2. 将测试用户的该字段写为 `operator value requiring backup`。
  3. POST `/api/admin/database/sync`，先以 `preview: true` 获取预览令牌，再携带令牌执行同步。
  4. 查询返回备份库的 `users.legacy_import_note`。
- 预期：普通字段原值完整保存到备份库，删除后仍可恢复。
- 修复前实际：同步接口返回 HTTP 200；备份表对应值为 `NULL`，不等于 `operator value requiring backup`，备份完整性断言失败。
- 定位证据：备份字段筛选对整个字段定义使用 `/GENERATED ALWAYS/i`；注释命中后普通字段也被排除在复制字段列表外。上一轮仅记录事实，未实施修复；本次修复见下节。
- 可重复用例：`tests/backend-api/schema-sync-regression.integration.mjs` 的 `ordinary field with generation-related comment is backed up without data loss`。
