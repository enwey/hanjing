## BIND-03：跨入口重复提交

- 预期：同一账号同一邀请码已有绑定进行中时，不重复提交。
- 复现：登录完成后补绑函数发起邀请码 A 请求，响应尚未处理时触发 app.onShow，仍读取 A；等待两者完成。
- 实际：bindDistribution 调用 2 次，预期 1 次。分别执行真实补绑函数及 app 生命周期，API 为模拟响应。
- 影响：额外请求和后端竞争；未证明产生重复数据库关系。
- 位置：mp-weixin-rewrite/app.js 的 tryBindPendingInvite 与 stores/session-store.js 的 bindPendingInviteCode。
- 原 app 生命周期内部去重仍通过；本条是跨 app/session 路径遗漏，不覆盖原通过历史。

## BIND-04：管理端绕过停用状态

- 预期：绑定患者不应撤销推广员的停用状态。
- 复现：准备 inactive 推广员 A、患者关联账号 B，以具备患者访问权限的管理员调用 bind-promoter。
- 实际：接口接受 A，写入关系并将 A 改为 active。原小程序接口的拒绝规则在此入口未生效。
- 风险：高；位置：hanjing-clinic-backend/routes/admin.js:6830、6846。隔离模型已复现，未实际更改后台账号。

## BIND-05：管理端形成循环

- 预期：任何绑定入口都不能将祖先绑定到其后代。
- 复现：已有 B→A 一级关系，将患者 B 的推广人设置为 A。
- 实际：新增 A→B 一级关系，与原关系组成环；接口不拒绝。
- 风险：高；影响团队层级与佣金归属可信度，本轮未实际结算佣金。
- 位置：hanjing-clinic-backend/routes/admin.js:6836～6844。小程序路由的循环检查结果不变，但不能代表该管理端入口。

## BIND-06：改绑覆盖两个级别

- 预期：一级推广人与二级祖先应与推荐层级对应，不能在改绑时不分级别变成同一个推广人。
- 复现：患者 B 已有一级上级 C、二级上级 D；管理员改绑 B 的推广人为 A。
- 实际：两行都被更新为 parent=A，保留 level=1 与 level=2，形成 A→B 一级及 A→B 二级。
- 证据：`[{parent:1,child:2,level:1},{parent:1,child:2,level:2}]`。
- 风险：高；佣金逻辑分别读取两个级别，存在同一人获得两级佣金的风险，未发起真实支付。
- 位置：hanjing-clinic-backend/routes/admin.js:6842，UPDATE 的条件只有 child_user_id。
- 状态：回归通过（隔离模块）。本项不依赖 BIND-RISK-01 的动态/快照规则，两个层级被统一覆盖已确定。

## BIND-07：失败响应与持久化状态不一致

- 预期：绑定接口失败时，不应留下本次新增的有效关系使用户误认为没有绑定。
- 复现：准备未绑定患者 → 调用管理端绑定 → 关系 INSERT 成功后，在推广员状态 UPDATE 注入数据库错误。
- 实际：接口返回 HTTP 500“操作失败”，新增一级关系仍保留。
- 风险：中；用户重试或后续小程序绑定会面对与提示不一致的状态。
- 依据：真实路由逐条调用 run；db.js 中 run 使用 pool.execute，未在此路由建立事务。隔离模型按逐条提交模拟，非真实 MySQL 故障注入。
- 状态：回归通过（隔离模块）；位置：hanjing-clinic-backend/routes/admin.js:6844～6852。
