### MALL-06：同账号自动刷新令牌阻断付款

- 现象：没有退出或更换账号，仅自动刷新令牌，页面提示“登录状态已变化”。
- 预期：同一账号的正常令牌刷新不应作为账号切换阻断已创建订单的后续付款或支付重试。
- 实际场景一：创建请求期间执行实际 `store.setAccessToken(...,{isRefresh:true})`，创建返回订单 ID 后，微信支付调用为 0，提示“登录状态已变化，请重新进入订单”。
- 实际场景二：首次取消支付后执行同账号刷新，再次提交，创建仍为 1 次，但总支付调用仍仅 1 次，第二次被阻断并提示去订单列表。
- 复现：有效地址及数量；在创建 API 模拟响应前刷新同账号令牌，或支付取消后刷新再提交；观察支付调用和提示。
- 证据：`stores/session-store.js:212` 刷新也增加 sessionRevision；`api/request.js:247` 实际刷新使用 isRefresh；`pages/product/detail.js:505、515、531` 比较版本。
- 风险：中，付款流程中断，用户须转其他入口处理已创建订单；未发现实际重复扣款。本轮模拟刷新事件，未向真实认证服务发请求。

### MALL-07：离开页面后仍发起支付

- 现象：商品详情和订单详情在等待支付参数期间卸载，参数迟到仍调用 `wx.requestPayment`。
- 预期：已离开、卸载的页面不应自动发起尚未启动的支付交互。
- 实际：两个页面各复现一次，卸载后支付调用均为 1，预期为 0。
- 复现：发起付款并挂起 `payOrder`；触发页面卸载事件（存在 onUnload 则执行）；随后返回支付参数；观察 wx 调用。
- 证据：`pages/product/detail.js:536`、`pages/order/detail.js:197`。商品详情没有卸载处理；订单详情卸载处理仅使加载请求失效，不影响待返回的付款参数。
- 风险：中，用户离页后仍可能被发起支付交互打断。本轮只确认业务函数发出了调用，未证明微信客户端一定弹窗，更未证明实际扣款。

### MALL-08：商品详情旧结果覆盖新结果

- 现象：商品详情连续加载，同一商品新价格先返回，旧价格后返回，最后显示旧数据。
- 预期：保留后发请求的新商品信息与价格。
- 实际：B 响应 name=new、price=2000 后，A 响应 name=old、price=1000 覆盖，最终 name=old。
- 复现：同一详情页发起 A、B 两次 loadProduct；先完成 B，再完成 A；检查 product。
- 证据：`pages/product/detail.js:160`。
- 风险：中，展示及结算预览可能使用旧价格；后端独立计价仍有保护，未证实按旧价成交。
- 与 MALL-03 区别：原项限定商城列表、订单列表、订单详情，本项是商品详情新入口，不重复统计原三页问题。

### MALL-09：订单详情静默刷新 401 不清空私有信息

- 现象：曾成功显示订单的详情页再次进入，静默刷新返回 401 后仍显示原订单及收货信息。
- 预期：明确鉴权拒绝后，不继续显示私有订单详情或旧操作按钮。
- 实际：`data.order` 仍为旧订单对象，含模拟收货联系人，且付款/取消标志仍在。
- 复现：先成功 loadOrder；随后 getOrderDetail 返回 statusCode=401；调用 loadOrder(id,{silent:true})（已加载页面 onShow 使用此模式）；检查 data.order。
- 证据：`pages/order/detail.js:163`，静默错误分支保留原订单。
- 风险：中，失效授权下继续展示缓存私有信息；没有验证真实跨账号读取，不声称跨账号泄露已发生。
- 与 MALL-04 区别：原项为订单列表并已通过，本项为订单详情。对照检查：非静默 401 能清空详情，商品初始网络错误能清空商品，均通过。
