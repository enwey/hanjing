### 复现过程与代码依据

1. **APT-1118-01**：放入同账号的过期微信会话 → 页面实际请求遇401 → 实际请求层调用模拟wx.login/续期接口 → 原请求重试成功。确认续期调用一次、令牌已更新，但列表仍loading=true、记录0；确认页loading=true、成员0、draft未加载。列表 `booking/index.js:115`～`:116` 和确认页 `confirm.js:95`～`:96` 用原始token相等判断请求归属，正常续期改变token后也把结果当旧会话丢弃。
2. **APT-1118-02**：正常加载本人和家人 → 通过实际成员选择函数选中家人 → 再次加载家人请求遇401并续期 → 第一次重载被旧token保护忽略 → 下一次加载保留逻辑也不认旧token，回退到self。观察选中patient从family变self。依据 `confirm.js:136`～`:139` 的memberOwnerToken比较。未真实提交给错误患者，但当前提交函数读取的就是被重置后的memberIndex。
3. **APT-1118-03**：实际详情loadPage发起 → 调用实际sessionStore.logout → 放行旧详情响应 → 观察isLoggedIn=false而appointmentLoaded=true、patientName为旧患者。`detail.js:170`开始等待详情与设置，后续写页面没有会话/加载代次保护；WXML只用appointmentLoaded控制详情显示。真实微信页面在这一过程中是否仍存活/可见待真机验证。
4. **APT-1118-04**：同一页面发出两次详情加载 → 新响应cancelled先返回 → 旧响应pending晚到，观察statusKey变回pending。详情loadPage没有按请求先后舍弃旧结果。受控响应时序仅说明模块健壮性，不是本次执行了真实取消。
5. **APT-1118-05**：正常经确认页加载成员 → 提交预约并挂起模拟成功响应 → 实际退出并切换B → 通过草稿存储入口写B草稿和B评估缓存 → 放行A创建结果。观察draftPreserved=false、assessmentPreserved=false、导航指向A成功页。`confirm.js:259`等待createAppointment后，`:275`～`:277`及`:346`～`:348`清缓存/跳转未再次核对请求所属会话。原guard只在提交前校验，不能覆盖等待创建响应期间的变化。
