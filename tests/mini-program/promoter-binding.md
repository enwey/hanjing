- 结论：当前实现未设置单个邀请码的累计邀请人数上限；同一个有效邀请码可供多个不同账号使用，不是一次性码。

## BIND-01：异常 scene 编码中断启动逻辑

- 现象/实际：传入 scene=`%ZZ`，onLaunch 抛出 `URI malformed`；后续绑定、全局异常与隐私回调注册代码未执行。
- 预期：异常外部参数不应中断启动流程。
- 复现：在隔离 app 的 onLaunch 输入 `{query:{scene:'%ZZ'}}`，检查是否抛出异常。
- 位置：mp-weixin-rewrite/app.js，parseInviteCodeFromLaunchOptions 中 decodeURIComponent。
- 风险等级：中；状态：回归通过（隔离模块）。异常参数的真实微信入口可达性尚未真机验证，不宣称整个小程序必然白屏。

## BIND-02：旧请求误删新邀请码

- 现象/实际：OLD 请求等待期间 pending_invite_code 更新为 NEW；OLD 返回“无效的邀请码”后，NEW 被删除，实际读取为 undefined。
- 预期：旧请求的结果不应删除尚未完成绑定的新邀请码。
- 复现：设置登录态及 OLD → 发起绑定并延迟响应 → 模拟后续邀请入口写入 NEW → OLD 返回无效邀请码 → 检查缓存。app 与 session 补绑函数分别复现。
- 影响：若 NEW 请求尚未发出或遭遇临时网络失败，后续重新进入时失去重试依据，可能遗漏推广归属。
- 位置：mp-weixin-rewrite/app.js 的 tryBindPendingInvite；stores/session-store.js 的 bindPendingInviteCode。
- 风险等级：中；状态：回归通过（隔离模块）。

## BIND-03：冷启动重复请求

- 现象/实际：登录态存在时，按顺序调用 onLaunch、onShow，首个请求未返回即发出第二个同码绑定请求；调用数 2，预期 1。
- 预期：同一启动过程同一邀请码只保留一个进行中的绑定请求。
- 复现：配置有效模拟登录态 → 两个生命周期均带 inviteCode=A → 延迟绑定 API → 统计调用次数。
- 影响：额外网络请求及后端事务竞争。数据库源码有 child_user_id + level 唯一索引与重复键处理，因此本项不等于证明数据库出现重复关系。
- 位置：mp-weixin-rewrite/app.js，onLaunch/onShow 均调用 tryBindPendingInvite。
- 风险等级：低；状态：回归通过（隔离模块）（跨入口修复完成；原历史保留）。

## BIND-04：禁用推广员被重新激活

- 现象/实际：邀请码所属推广员 status=inactive；其他用户绑定该码，路由执行状态更新，推广员变为 active。
- 预期：被邀请用户不能通过绑定操作撤销管理端禁用状态。
- 复现：隔离数据库准备 inactive 推广员 A → 用户 B 提交 A 的有效邀请码 → 检查状态与返回结果，实际绑定成功并激活 A。
- 依据：管理端 promoter.vue 将非 active 显示为“已禁用”；admin.js 提供推广员状态修改；client.js 绑定路由仅按邀请码查询且无条件设置 active。
- 影响：管理端禁用失效；佣金及推广员权限判断中使用 active，存在进一步业务风险，但本轮未实际结算佣金。
- 位置：hanjing-clinic-backend/routes/client.js:7065、7097。
- 风险等级：高；状态：回归通过（隔离模块）（跨入口修复完成；原历史保留）。

## BIND-05：循环推荐与自我二级关系

- 现象/实际：已有 B → A 的一级关系，B 再绑定 A 的邀请码，路由成功写入 A → B（一级）及 B → B（二级）。
- 预期：推荐关系不得形成祖先/后代循环，任何级别不得出现自己推荐自己。
- 复现：隔离数据建立 parent=2、child=1、level=1 → 用户 2 提交用户 1 的邀请码 → 检查关系表。
- 实际证据：新增 `{parent:1,child:2,level:1}` 和 `{parent:2,child:2,level:2}`，未被直接自邀检查拒绝。
- 影响：团队关系异常；二级佣金读取该关系，存在自购返佣归属错误风险，未进行真实结算验证。
- 位置：hanjing-clinic-backend/routes/client.js，绑定路由的 self 检查及 grandParent 插入。
- 风险等级：高；状态：回归通过（隔离模块）（跨入口修复完成；原历史保留）。

## BIND-RISK-01：后补上级的二级归属

- 现象：先让 B 绑定 A，再让 A 绑定 C，最终存在 C → A → B 的一级链路，但无 C → B 的二级记录。反过来先绑定 A 到 C，再绑定 B 到 A，则有二级记录。
- 期望待确认：二级关系按当前层级动态维护，还是只在被邀请人首次绑定时固定快照？
- 实际：当前代码采用首次绑定时的祖父关系写入；佣金计算直接读取已保存 level=2 关系。因此不同绑定顺序会影响未来二级归属。
- 复现：隔离数据按上述两个顺序调用绑定路由并比较关系行。
- 当前风险等级：高；状态：回归通过（隔离模块）。2026-10-22 已重新执行专项及绑定顺序、旧缓存检查；[独立回归](../2026-10-22-all-defects-regression-03.md)。首轮失败与开发历史保留，真实数据库未验收。
