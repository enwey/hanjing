## 当前规则

- 详情入口与“我的患者”列表保持一致：必须存在当前推广员推荐的该患者预约。只有用户绑定关系或佣金记录，不放行完整患者档案；无权限和不存在统一返回 404。
- 预约只返回本人推荐的记录；病历仅返回关联这些预约且患者一致的记录，最新病历从可见记录选取。
- 订单仅包含本人推荐预约关联订单，或明确归属当前患者且给本人产生佣金的订单。通过预约或收银上下文 patient_id 确认患者，不以同一付款账号推断；明细和消费合计使用同一条件。
- 设备及佩戴数据必须通过绑定病历或治疗档案追溯到本人推荐预约；无法明确关联的历史档案不回退为全量展示。
- ESS/鼾声评估只返回本人推荐预约明确引用且患者一致的报告，不再取整个账号或患者最新报告。历史 patient_id 为空的报告仍须账号匹配且被该患者预约明确引用。
- 家庭成员仅返回同账号中各自存在本人推荐预约的患者，不附带家庭成员评估数据。
- 页面“账户消费总额”改为“关联订单消费”，说明同步明确为本人推荐预约相关记录；其余布局及业务未改。
- 未接入门店/系统查看范围；佣金归属和提现操作逻辑未改。

## 验证

执行 `node tests/promoter/patient-personal-scope.integration.mjs`：临时 schema 克隆表结构，独立构造两个推广员、同一患者的不同推荐预约、同一账号的其他家庭成员、不同归属订单/病历/设备/评估；通过真实鉴权中间件访问 Express HTTP，结束删除临时库。

5 组通过：

1. A 只见本人预约及临床记录、设备打卡和明确归属订单；合计与明细一致。
2. B 查看同一患者时只见 B 的记录，无法混入 A 的记录。
3. 列表与详情权限一致；其他家庭成员、只有绑定关系的患者、伪造查询参数中的推广员 ID 不能绕过限制。
4. 本人佣金可开放明确归属患者的订单，但不开放该订单另一推广员推荐的临床记录。
5. 评估引用取消后不回退其他报告；推荐归属撤销后使用原登录令牌也立即拒绝详情。

推广端 `npm run typecheck`、`npx vite build` 均通过；构建仅有既有大 chunk 提示。后端语法与 Git 差异检查通过。本地后端已重启。未进行浏览器视觉/点击或正式环境验收，未提交 GitHub。
